# 研究团队介绍网页构建框架

更新日期：2026-07-31

## 1. 文档定位

这是 Awesome Team 构建研究团队独立介绍网页的**项目级关键参考文档**。它定义的核心不是单独的论文数据库，也不只是处理官网停滞团队，而是：

1. 一个团队介绍网页应该回答什么问题；
2. 页面应由哪些稳定模块组成；
3. 每个模块需要什么数据和证据；
4. 如何把团队、人物、项目、论文和研究方向组织成连贯叙事；
5. 如何验证页面中的判断；
6. 如何持续更新和复用到其他团队。

**论文检索与归属核验是这套网页框架的数据核心。** 团队官网通常不会完整、持续地展示研究论文，因此页面质量很大程度上取决于我们能否从 GitHub、负责人发表列表、作者单位、论文原文、项目页和模型社区中恢复一个可信的公开论文工作集。

因此，本文分为两个互相依赖的层次：

```text
研究团队介绍网页
  ├─ 页面框架：信息架构、叙事顺序、交互、视觉与完成标准
  └─ 证据框架：团队身份、人物任职、项目活动、论文检索与归属
```

适用对象包括：

- 官网信息完整、希望获得更系统研究画像的团队；
- 官网停止更新、迁移或只保留历史介绍的团队；
- 官网仍可访问，但没有论文目录或研究项目列表的团队；
- 研究成果分散在 GitHub、负责人主页、论文和模型社区的团队；
- 公开组织边界比传统实验室更松散的企业研究团队或开源组织。

目标不是复制官网，也不是恢复团队内部组织结构，而是构建一个有明确时间范围、证据来源和归属边界的**公开研究介绍网页**。

这份文档补充 [AI 研究团队采集方法](TEAM_COLLECTION_METHOD.md)：后者决定团队是否进入 Awesome Team，本框架决定团队进入目录后，独立介绍网页如何研究、组织、实现和验收。

## 2. 介绍网页的核心框架

### 2.1 页面必须回答的七个问题

一个合格的团队介绍网页，应让读者在不离开页面的情况下理解：

1. **这是谁？** 团队名称、母体机构、历史沿革和组织边界；
2. **现在研究什么？** 当前研究方向及其公开依据；
3. **现在是否活跃？** 论文、代码、模型和项目的近期信号；
4. **哪些人构成公开研究网络？** 当前负责人和研究者样本；
5. **做出了什么？** 代表项目、模型、数据集、工具和 benchmark；
6. **发表了什么？** 可搜索、可筛选、可解释归属的论文工作集；
7. **为什么可以相信？** 数据来源、统计口径、证据标签和限制。

页面不是团队官网的镜像，而是一个面向研究发现的结构化入口。它应帮助读者完成三个动作：

- 快速判断团队是否值得继续关注；
- 找到团队当前研究方向、人物、项目和论文；
- 回到原始来源核验页面中的结论。

### 2.2 标准页面信息架构

独立介绍页默认采用以下模块。可以因公开数据不足而缩减，但顺序和职责应尽量保持稳定。

| 模块 | 回答的问题 | 最低数据要求 | 主要交互 |
|---|---|---|---|
| Header / Navigation | 页面有哪些内容 | 模块锚点、团队入口、主目录返回入口 | 锚点导航 |
| Hero | 这个团队为何值得介绍 | 团队名、一句话定位、核心统计 | 进入论文或项目 |
| Evidence Note | 页面如何处理证据缺口 | 主要来源和边界声明 | 跳到方法说明 |
| Current Team Profile | 当前研究什么 | 方向、团队简介、母体关系 | 方向浏览 |
| Activity Signals | 是否仍然活跃 | 论文、仓库、模型或项目时间信号 | 查看近期活动 |
| Abstract Keywords | 公开论文体现哪些研究重心 | Abstract 工作集和可复算统计 | 关键词摘要 |
| Public People | 哪些公开人物可核验 | 当前任职来源、角色和研究方向 | 打开人物主页 |
| Public Projects | 有哪些研究系统 | 项目、模型、数据集、代码及来源 | 打开项目 |
| Recent Publications | 有哪些论文以及为何归属 | 标题、作者、年份、摘要、归属证据 | 搜索、筛选、展开 |
| Source & Attribution | 页面如何得出结论 | 来源清单、更新时间、归属规则 | 打开原始来源 |
| Footer | 如何返回和继续浏览 | 团队标识、主目录入口 | 返回顶部或目录 |

### 2.3 页面叙事顺序

页面应遵循“结论 → 证据 → 细节 → 方法”的阅读路径：

```text
团队当前画像
  ↓
近期活跃证据
  ↓
研究方向与关键词
  ↓
人物和项目
  ↓
逐篇论文
  ↓
来源、归属规则和限制
```

不要一进入页面就给读者一个没有上下文的论文长列表。Hero 和团队画像先建立认知，活跃信号解释为什么该团队仍值得关注，人物与项目补足研究网络，论文浏览器承担深度探索，方法说明负责建立信任。

### 2.4 各模块的内容规则

#### Hero

- 标题必须来自团队最有辨识度的现状，不写通用宣传口号；
- 一句话介绍应同时表达历史位置和当前研究重心；
- 核心数字最多保留 3–4 项；
- 数字必须来自页面数据文件，而不是只写在 HTML 中；
- 主行动优先指向论文、项目或研究方向。

#### Evidence Note

- 当官网停滞或数据分散时必须展示；
- 用一段话说明页面使用了哪些替代来源；
- 明确“官网未更新”不等于“团队停止研究”；
- 明确公开工作集不等于完整内部名录。

#### Current Team Profile

- 简介由团队身份、当前人物自述、项目和近期论文共同支持；
- 历史方向与当前方向分开；
- 方向数量建议为 5–8 个；
- 不根据单篇论文把偶发主题升级为团队长期方向。

#### Activity Signals

- 论文时间、仓库推送、模型发布和项目更新分别展示；
- 不把 GitHub `pushed_at` 写成论文发布日期；
- 不把 Stars 写成论文影响力；
- 至少说明时间窗口和截止日期。

#### Abstract Keywords

- 只使用有 Abstract 的论文；
- 同时展示论文工作集总数和 Abstract 统计分母；
- 合并同义表达，过滤论文写作套话；
- 使用跨论文覆盖率，不用简单总词频制造视觉噪声；
- 图像之外保留结构化 JSON 和文字摘要。

#### Public People

- 只展示有当前任职证据的人物；
- 角色名称遵循公开来源；
- 页面称其为“公开成员样本”或“公开研究网络”；
- 不推断完整组织层级、汇报关系或内部人数。

#### Public Projects

- 项目入口保持原始组织归属；
- 跨 GitHub Organization 发布不自动改变项目归属；
- 区分模型、数据集、benchmark、框架和应用；
- 说明项目与团队建立关联的来源。

#### Recent Publications

- 每篇论文保留归属证据类型；
- 支持标题、作者、Abstract 关键词搜索；
- 支持方向、年份、归属证据和时间排序；
- 展开后展示 Abstract、作者、Venue、论文、代码和证据入口；
- 缺少 Abstract 时明确说明，不生成伪摘要；
- 论文数量较多时必须分页或渐进加载。

#### Source & Attribution

- 展示主要来源及其用途；
- 解释“官方团队发布”和“负责人论文索引”的区别；
- 公开数据同步或核验日期；
- 写清页面没有声称什么；
- 让读者可以回到一手来源复查。

### 2.5 数据缺失时的降级策略

不是每个团队都有与 Youtu 相同的数据量。模块可以降级，但不能伪造完整性。

| 缺失内容 | 页面处理 |
|---|---|
| 没有当前官网 | 保留历史身份页，使用 GitHub、人物和论文重建当前画像 |
| 没有官方论文目录 | 从官方仓库、负责人索引和论文 affiliation 建立工作集 |
| 没有足够 Abstract | 省略关键词图，保留论文列表并说明覆盖缺口 |
| 没有独立 GitHub 组织 | 展示项目仓库，但降低组织级归属判断 |
| 没有公开完整成员 | 展示可核验人物样本，不补齐人数 |
| 没有近期仓库活动 | 以论文、模型或项目发布时间作为其他活跃信号 |
| 论文归属不足 | 保持候选状态，不进入正式统计 |

### 2.6 页面实现原则

- **数据驱动**：统计、列表和筛选来自结构化数据，不在多个文件重复维护；
- **证据可见**：页面中的重要判断都有来源入口；
- **口径一致**：总论文数、Abstract 数、项目数和活跃仓库数可复算；
- **渐进披露**：先给研究画像，再允许展开论文细节；
- **响应式**：桌面和移动端都能浏览全部模块；
- **可访问**：语义标题、表单标签、替代文字、键盘操作和可读对比度完整；
- **可复用**：团队专属视觉可以变化，数据结构和核心模块保持一致；
- **可维护**：同步脚本、生成脚本、数据、页面和校验入口成套存在。

### 2.7 统一框架与团队化表达

后续团队页面应共享同一套研究和交互框架，但不应机械复制 Youtu 的视觉和文案。

必须统一：

- 页面回答的七个核心问题；
- 团队、人物、项目和论文的数据关系；
- 来源证据与归属标签；
- 论文搜索、筛选、展开和分页行为；
- 统计口径和更新时间；
- Evidence Note 与 Source & Attribution；
- 移动端、键盘操作和可访问性标准；
- 同步、生成、构建和校验流程。

应根据团队变化：

- Hero 标题和开场叙事；
- 品牌色、字体气质、留白和视觉节奏；
- 最值得突出的活动信号；
- 研究方向的组织方式；
- 项目卡片的类别和排序；
- 关键词图的研究词汇与配色；
- 历史背景和当前转型的表达；
- 团队特有的证据缺口。

页面设计应从团队事实出发。例如：

- 官网停滞但 GitHub 活跃的团队，可以突出“公开研究网络仍在运行”；
- 论文丰富但项目较少的学术实验室，可以把人物、研究主题和论文浏览作为主轴；
- 模型与数据集驱动的开源团队，可以强化版本、模型卡、数据集和技术报告；
- 多个联合组织共同发布成果的团队，应把归属边界与合作网络放在显著位置。

### 2.8 网页层面的完成定义

一个独立介绍页只有同时满足以下条件才算完成：

1. 首屏能准确说明团队身份、当前价值和页面范围；
2. 读者可以在 30 秒内找到研究方向、人物、项目和论文入口；
3. 页面中的核心数字全部由结构化数据生成；
4. 每篇正式论文都有可解释的纳入原因；
5. 数据缺口和不确定性在页面中可见；
6. 桌面与移动端均无内容丢失或横向溢出；
7. 搜索、筛选、分页、展开和外链行为可用；
8. 图片具有替代文字，表单具有标签，键盘可完成核心浏览；
9. 原始来源、数据日期和方法说明可以被读者访问；
10. 同步脚本和生成流程可以在下一次更新时复现页面。

## 3. 核心原则

### 3.1 官网不是唯一事实源

官网可以证明团队的历史身份，但官网停止更新不能单独证明团队已经停止研究。判断当前状态时，应把团队看成由以下节点组成的公开研究网络：

```text
团队历史身份
  ├─ 维护中的 GitHub / 模型组织
  ├─ 现任负责人和资深研究者
  ├─ 负责人公开论文索引
  ├─ 论文首页、作者单位和通信信息
  ├─ 项目页、模型卡、数据集和技术报告
  └─ 多个来源之间的相互链接
```

### 3.2 “团队活跃”与“论文归属”分开证明

这是整个框架中最重要的区分：

- GitHub 最近仍在更新，可以证明代码或项目活跃；
- 负责人最近仍在发表，可以证明该研究网络仍有产出；
- 论文明确署名团队、由官方仓库发布，才能更强地证明论文属于团队；
- 负责人参与一篇论文，不自动等于“官方团队发布”；
- 作者当前在某团队任职，不自动证明其过去论文属于当前团队。

每个页面需要同时回答两个问题：

1. **团队现在是否仍然活跃？**
2. **这篇论文为什么被纳入该团队的公开工作集？**

### 3.3 证据随结论保存

不要只保存结论。每个团队、人物、项目和论文条目都应保留：

- 来源 URL；
- 来源类型；
- 检索或同步日期；
- 来源支持的具体结论；
- 证据强度；
- 不能由该证据推出的内容。

### 3.4 公开工作集不等于内部名录

页面统一使用“公开研究档案”“公开工作集”“公开成员样本”等表述，不使用：

- “完整团队成员”；
- “该团队全部论文”；
- “内部组织架构”；
- 没有公开依据的职级、汇报关系或共同负责人关系。

## 4. 开始检索前先固定边界

每个团队在检索前建立一张范围卡片。

| 字段 | 说明 |
|---|---|
| `team_name` | 当前公开团队名 |
| `parent_organization` | 母体机构 |
| `aliases` | 历史名、简称、中英文名、品牌名 |
| `historical_homepage` | 旧官网或历史身份页 |
| `activity_window` | 默认最近 24 个月 |
| `publication_window` | 独立页通常使用最近 2–3 年 |
| `cutoff_date` | 本轮核验截止日期 |
| `known_leaders` | 已知负责人或资深研究者 |
| `known_code_orgs` | 已知 GitHub / Hugging Face 等组织 |
| `boundary_note` | 团队与母体、事业群、联合实验室的边界 |

检索前应先列出名称变体。例如：

```text
Tencent Youtu Lab
Youtu Lab
Tencent Youtu
腾讯优图实验室
TencentYoutuResearch
```

名称变体用于搜索，不代表这些名称在所有时间和来源中完全等价。只有来源明确连接时，才能合并为同一研究实体。

## 5. 七个检索维度

### 5.1 历史身份与组织锚点

先证明“这个团队确实存在并属于该母体机构”。

优先检索：

- 母体机构官网中的团队介绍；
- 团队旧官网；
- 官方新闻稿、招聘页和技术博客；
- 官方 GitHub Organization 的简介和官网链接；
- 官方模型或数据集组织页；
- 论文或项目页中的团队全称。

历史页面即使停更，也可以作为身份锚点，但不能独立证明当前活跃。

### 5.2 GitHub 与公开代码网络

GitHub 往往是官网停滞后最稳定的活动入口。

需要检查：

- Organization 是否由母体机构或团队公开页面链接；
- Organization 简介、头像、官网链接和 verified domain；
- 仓库创建时间、最近推送时间、归档状态；
- README 是否给出论文标题、arXiv、DOI、项目页和作者；
- 仓库是否在多个年份持续发布研究项目；
- Release、模型权重、数据集和 benchmark 是否仍在维护；
- 仓库是否迁移到母体机构、联合组织或项目专属组织；
- 同一个项目是否由负责人主页或论文反向链接。

GitHub 信号的正确解释：

| 信号 | 可以说明 | 不能单独说明 |
|---|---|---|
| 最近 `pushed_at` | 代码仍在维护 | 论文刚发表 |
| 官方组织拥有仓库 | 项目与团队存在强关联 | 仓库内每位作者都是团队成员 |
| README 链接论文 | 代码与论文可以对应 | 论文一定是团队官方发布 |
| 项目专属组织 | 项目存在稳定公开入口 | 项目专属组织等同于团队组织 |
| Stars / Forks | 代码采用度 | 学术引用量或研究质量 |

推荐搜索式：

```text
site:github.com "<团队名>"
site:github.com "<负责人姓名>" "<母体机构>"
site:github.com "<论文标题>"
org:<候选组织> arxiv
org:<候选组织> paper
```

### 5.3 负责人和资深研究者

当团队没有论文目录时，负责人主页通常是最重要的论文入口。

人物进入“当前公开成员样本”前，应至少满足一项：

- 当前个人主页明确写出团队名和现任职务；
- 母体机构当前员工页明确列出团队或研究角色；
- 当前团队页明确列出该人物；
- 当前项目或论文资料与个人主页互相指向，并有额外交叉证据。

从人物主页提取：

- 当前任职及其表述原文；
- 研究方向；
- 近 2–3 年论文列表；
- 项目和代码链接；
- Google Scholar、ORCID、DBLP 等身份入口；
- 主页最后更新时间或论文列表的最新年份。

负责人论文列表是**高价值候选集**，但不是自动的“团队官方论文目录”。其中可能包含：

- 入职前成果；
- 个人学术合作；
- 与其他团队联合完成的项目；
- 没有团队署名的外部合作。

因此，负责人列表中的论文应标记为“负责人公开论文索引”，并继续进行逐篇验证。

推荐搜索式：

```text
"<负责人姓名>" "<团队名>"
"<负责人姓名>" publications
"<负责人姓名>" site:scholar.google.com
"<负责人姓名>" site:dblp.org
"<负责人姓名>" "<母体机构>" filetype:pdf
```

### 5.4 论文发现与候选集建立

论文候选来源按优先级排列：

1. 团队官方论文页；
2. 官方研究仓库中明确链接的论文；
3. 现任负责人或资深研究者的公开论文索引；
4. 团队项目页、模型卡或数据集页链接的技术报告；
5. arXiv、DBLP、OpenAlex、Crossref、Semantic Scholar 中的作者或机构检索；
6. Google Scholar 精确标题检索；
7. 搜索引擎结果，用于发现候选，不作为最终归属证据。

数据库的职责应分开：

| 来源 | 主要用途 | 注意事项 |
|---|---|---|
| arXiv | 标题、作者、摘要、提交时间、PDF | 提交时间不一定等于会议发表时间 |
| DBLP | 计算机领域书目信息与作者消歧 | 通常不提供团队级 affiliation |
| OpenAlex | 论文身份、摘要、机构候选 | affiliation 需要回到原文核验 |
| Crossref | DOI、期刊或会议元数据 | 标题匹配必须严格 |
| Semantic Scholar | 论文身份与引用量 | 引用数字必须保存来源和日期 |
| Google Scholar | 精确标题和作者检索入口 | 搜索结果不宜作为唯一元数据源 |

### 5.5 论文内部证据

对于归属不清的论文，需要打开论文 HTML 或 PDF，检查以下位置：

1. 首页作者单位；
2. 作者姓名与 affiliation 编号的对应关系；
3. 通信作者和邮箱域名；
4. 页眉、页脚、团队标识和项目标识；
5. Acknowledgements；
6. Appendix 中的作者贡献与机构说明；
7. 项目页和代码链接；
8. PDF 元数据只作为辅助，不作为主要证据。

不同证据的解释：

| 论文内部信号 | 证据强度 | 正确用法 |
|---|---:|---|
| 作者 affiliation 明确写团队全称 | 强 | 可证明对应作者在该论文中的团队归属 |
| 作者 affiliation 只写母体机构 | 中 | 可证明母体机构参与，不能自动缩小到具体团队 |
| 通信邮箱使用母体机构域名 | 中低 | 支持机构关联，不能独立证明团队 |
| 论文首页出现团队 Logo | 中低 | 支持品牌或项目关联，必须结合 affiliation、仓库或项目页 |
| Acknowledgements 提到团队 | 中低 | 可能只是资源、实习或资助支持 |
| 项目页由官方团队域名托管 | 中高 | 与论文标题、作者和仓库一致时很有价值 |
| PDF 使用母体机构模板 | 低 | 模板可能被联合项目或个人使用 |

#### 为什么 Logo 不能单独决定归属

论文上的 Logo 可能代表：

- 作者所属机构；
- 联合项目参与方；
- 资助方；
- 提供算力或数据的单位；
- 项目品牌；
- 通用演示模板。

因此，“论文上有团队 Logo”只能作为支持证据。至少还需要以下一项：

- 对应作者 affiliation 明确写团队名；
- 官方团队仓库链接该论文；
- 当前负责人主页将论文列入团队相关成果；
- 官方项目页同时连接论文和团队；
- 母体机构研究页面明确发布该论文。

#### 为什么作者机构也要按时间判断

论文中的 affiliation 是**论文发生时的机构证据**；个人主页中的任职是**当前状态证据**。两者不可互相替换。

例如：

- 作者 2026 年加入团队，不应把其 2023 年论文自动归入该团队；
- 作者当前主页列出旧论文，可以说明该论文属于个人研究轨迹，不代表当前团队发布；
- 作者在论文中同时列出两个机构，需要保留双重 affiliation，不能只选择其中一个；
- 只有母体机构名而没有团队名时，应标记为“母体机构署名”，不能升级成“团队明确署名”。

### 5.6 模型、数据集、项目页与社区平台

研究团队的当前产出不一定以论文目录为中心，还应检索：

- Hugging Face Organization 和模型卡；
- Papers with Code 项目链接；
- 官方 ModelScope、GitHub Releases 或数据集页面；
- benchmark 排行榜；
- 技术报告和系统卡；
- 官方演示、项目主页和文档站；
- 母体机构技术博客或开发者社区。

检查模型卡和项目页是否包含：

- 组织所有者；
- 论文或技术报告；
- 作者和联系方式；
- 官方仓库；
- License；
- 发布时间和最近更新时间；
- 与团队或母体机构的明确关系。

### 5.7 时间与连续性

独立页面不仅展示数量，还要展示连续性。

分别保存：

- `published_at`：论文公开或正式发表时间；
- `created_at`：仓库创建时间；
- `pushed_at`：仓库最后推送时间；
- `released_at`：模型或版本发布时间；
- `checked_at`：本次核验时间；
- `current_role_checked_at`：人物任职核验时间。

不要把这些时间混为一个“最新时间”。

判断团队仍然活跃时，优先寻找：

- 最近 24 个月多个独立月份或年份持续出现成果；
- 至少两种活动类型，例如论文加代码、模型加评测；
- 多个来源互相指向；
- 不只是旧仓库的一次自动更新；
- 不只是单个成员的一篇外部合作。

## 6. 证据等级与归属标签

### 6.1 来源证据等级

| 等级 | 定义 | 示例 |
|---|---|---|
| A：直接官方证据 | 来源直接表达团队与成果的关系 | 官方团队论文页、官方团队仓库、论文明确写团队 affiliation |
| B：强关联证据 | 当前团队核心人物或母体官方渠道明确列出成果 | 现任负责人论文索引、母体机构研究博客、官方项目页 |
| C：支持证据 | 能支持但不能独立完成团队级归属 | 母体机构邮箱、论文 Logo、Acknowledgements、模型卡 |
| D：发现线索 | 只能用于找到候选 | 搜索结果、第三方榜单、聚合站、非官方转载 |

正式纳入论文工作集至少需要 A，或 B 加另一条独立的 B/C 证据。只有 C 或 D 时，论文保持候选状态。

### 6.2 论文归属标签

建议所有独立页面统一使用以下标签：

| `kind` | 页面标签 | 使用条件 |
|---|---|---|
| `official_team_release` | 官方团队发布 | 官方团队论文页、仓库或项目页明确发布 |
| `paper_team_affiliation` | 论文明确团队署名 | PDF/HTML 中对应作者 affiliation 明确出现团队名 |
| `current_leader_publication_index` | 负责人公开论文索引 | 现任负责人主页明确列出 |
| `parent_organization_release` | 母体机构研究发布 | 母体官方渠道发布，但具体团队边界不足 |
| `official_project_ecosystem` | 官方项目生态 | 官方模型、数据集或 benchmark 连接论文 |
| `candidate_unresolved` | 候选，归属待核验 | 已发现论文但团队级证据不足 |

同一论文有多种证据时，保存全部证据，展示时选择最强标签。

### 6.3 常见证据组合

| 证据组合 | 处理建议 |
|---|---|
| 官方团队仓库 + README 论文链接 | 纳入，通常标记“官方团队发布” |
| 负责人当前任职 + 负责人论文索引 | 纳入公开工作集，标记“负责人公开论文索引” |
| 论文团队 affiliation + 官方项目页 | 纳入，标记“论文明确团队署名”或更强标签 |
| 只有母体机构 affiliation | 可进入母体机构候选集，不能自动进入具体团队 |
| 只有团队 Logo | 不纳入，继续找 affiliation、仓库或负责人证据 |
| 只有作者当前在职信息 | 不足以归属历史论文 |
| 只有 GitHub 用户名或 README 自述 | 保持候选，寻找官方反向链接 |
| 多个成员共同署名但无团队证据 | 支持研究网络关联，仍需额外团队级证据 |

## 7. 从零构建独立页面的工作流

### 阶段 1：建立团队身份卡

1. 确认团队名、母体机构、别名和历史官网；
2. 保存至少一条官方身份来源；
3. 定义最近 24 个月活跃窗口；
4. 记录官网最后可见更新时间；
5. 写出团队与母体、事业群或联合实验室的边界说明。

输出：

```text
team-profile
source-register
alias-list
boundary-note
```

### 阶段 2：恢复当前研究网络

1. 搜索维护中的 GitHub / Hugging Face 组织；
2. 找到当前负责人和资深研究者；
3. 核验人物当前任职；
4. 提取研究方向、项目和论文索引；
5. 建立“来源互相指向”图。

至少应形成：

```text
历史官网 → 团队身份
当前人物主页 → 当前任职
GitHub / 项目页 → 当前代码活动
论文 / 技术报告 → 当前研究产出
```

### 阶段 3：建立论文候选集

按来源分别抓取，不要在抓取阶段抹掉来源差异：

```text
official_team_papers[]
official_repository_papers[]
leader_indexed_papers[]
paper_affiliation_candidates[]
project_ecosystem_papers[]
```

每条候选至少保存标题、年份、来源 URL 和发现路径。

### 阶段 4：逐篇核验与去重

1. 优先使用 arXiv ID、DOI 去重；
2. 没有稳定标识符时使用严格规范化标题；
3. 检查版本差异、会议版和期刊扩展版；
4. 打开论文原文核验 affiliation；
5. 合并多条归属证据；
6. 记录无法解决的冲突，不猜测。

标题规范化只用于匹配，不应覆盖公开标题：

```text
lowercase
Unicode 规范化
去除多余空格
统一连字符
保留原始标题
```

### 阶段 5：补齐论文元数据

对已确认论文补齐：

- 标题；
- 作者；
- 年份和完整日期；
- Venue；
- arXiv ID / DOI；
- Abstract；
- 论文原文；
- 代码或项目页；
- 研究方向；
- 归属标签和证据 URL；
- 来源核验日期。

只有获取到 Abstract 的论文才进入：

- 摘要搜索；
- 中文 TL;DR；
- 关键词覆盖率；
- 基于摘要的方向归纳。

关键词统计必须明确“论文工作集总数”和“有 Abstract 的统计分母”，两者不能混写。

### 阶段 6：形成当前研究方向

研究方向不应只由编辑者凭标题印象决定。可以组合：

1. 团队或负责人公开自述；
2. 论文标题和 Abstract；
3. 仓库和项目标签；
4. 最近 24 个月的方向计数；
5. 摘要关键词跨论文覆盖率。

推荐同时展示：

- 编辑后的 5–8 个方向卡片；
- 按论文标签汇总的数量；
- 基于 Abstract 的关键词覆盖率；
- 代表项目和近期仓库活动。

### 阶段 7：生成页面

推荐独立页面结构：

1. **Hero**：一句话说明为什么需要重建该团队的公开档案；
2. **Evidence Note**：说明官网停滞与替代证据；
3. **Current Team Profile**：当前公开研究方向和团队边界；
4. **Activity Signals**：论文、仓库、模型和项目的活动信号；
5. **Abstract Keywords**：研究关键词覆盖率；
6. **Public People**：公开负责人和研究者样本；
7. **Public Projects**：模型、数据集、Agent、benchmark 和工具；
8. **Recent Publications**：可搜索、筛选、展开的论文工作集；
9. **Source & Attribution**：数据来源、标签和不声称的内容。

页面文案应直接暴露限制。例如：

> 本页是由维护中的研究仓库、当前负责人主页和论文署名重建的可核验公开工作集，不是团队内部成员或完整论文名录。

## 9. 冲突与不确定性处理

### 9.1 来源冲突

当来源冲突时：

1. 优先使用时间更近的一手来源；
2. 区分“论文发表时任职”和“当前任职”；
3. 不删除旧事实，给事实加时间；
4. 同时保存冲突来源；
5. 无法判断时降低证据等级。

### 9.2 团队更名、合并或拆分

不要因为人员和项目相似就自动合并团队。应检查：

- 官方是否宣布更名或合并；
- GitHub 是否跳转或迁移；
- 负责人是否明确描述继承关系；
- 新旧名称是否在论文、项目和招聘信息中共同出现；
- 母体组织是否发生变化。

没有明确继承证据时，保留两个实体并通过备注关联。

### 9.3 联合实验室与跨组织项目

联合成果需要保留所有公开 affiliation。页面可以把论文纳入团队工作集，但必须：

- 展示联合属性；
- 保留原始项目组织；
- 不把合作方成员写成该团队成员；
- 不因代码位于第三方组织而改变论文的原始归属。

### 9.4 没有找到足够论文

“没有找到”也是一个需要记录的检索结果。保存：

- 使用过的名称变体；
- 检索过的平台；
- 时间范围；
- 找到但排除的候选及原因；
- 下一次建议复查日期。

不要用低质量候选填满页面。

## 10. 自动化与人工核验的分工

适合自动化：

- GitHub 仓库列表和 `pushed_at`；
- 负责人论文 HTML 列表解析；
- arXiv 元数据和 Abstract；
- DOI / arXiv ID 去重；
- 标题规范化和严格匹配；
- 方向初步分类；
- 关键词覆盖率；
- JSON、JavaScript 和链接完整性校验。

必须保留人工核验：

- 团队与母体边界；
- 人物是否为现任；
- 论文 affiliation 与作者映射；
- Logo 和 Acknowledgements 的语义；
- 联合项目的归属表达；
- 团队更名和继承关系；
- 证据冲突；
- 页面是否产生超出公开来源的暗示。

## 11. 页面发布前检查清单

### 团队身份

- [ ] 有官方或母体机构来源证明团队身份；
- [ ] 记录官网是否停更，而不是直接推断团队停止；
- [ ] 团队与母体、事业群、联合实验室边界清楚；
- [ ] 名称变体已记录。

### 当前活跃性

- [ ] 时间窗口明确；
- [ ] 至少有论文、代码、模型、项目中的两类活动信号；
- [ ] GitHub 推送时间没有被写成论文发表时间；
- [ ] 单个成员的一篇合作论文没有被夸大为团队持续活跃。

### 人物

- [ ] 每位人物有当前任职证据；
- [ ] 角色名称来自公开原文；
- [ ] 没有推断内部层级；
- [ ] 负责人论文索引与官方团队发布分开标记。

### 论文

- [ ] 每篇论文保留发现来源和归属来源；
- [ ] arXiv / DOI / 标题去重完成；
- [ ] affiliation 对应到具体作者；
- [ ] 只有母体机构时没有擅自缩小到团队；
- [ ] Logo、邮箱和 Acknowledgements 没有被当作唯一证据；
- [ ] 入职前论文没有因当前任职被错误归属；
- [ ] 无法核验的候选保持 unresolved。

### 数据与统计

- [ ] 论文工作集总数与 Abstract 数量分开；
- [ ] 关键词覆盖率只使用有 Abstract 的论文；
- [ ] 代码 Stars 与论文引用量分开；
- [ ] 引用量有来源和核验日期；
- [ ] 所有统计可以从数据文件复算。

### 页面表达

- [ ] 明确说明公开工作集不等于完整内部名录；
- [ ] 页面展示证据类型和来源入口；
- [ ] 搜索、年份、方向和归属筛选可用；
- [ ] 数据更新时间可见；
- [ ] 没有使用无法由来源支持的确定性措辞。

## 12. Youtu 案例如何应用本框架

Tencent Youtu 页采用了以下证据组合：

| 页面内容 | 主要来源 | 页面中的解释 |
|---|---|---|
| 历史团队身份 | 旧官网 | 只作为历史身份入口 |
| 当前代码活动 | `TencentYoutuResearch` | 展示仓库数量和近期推送 |
| 当前人物 | Ke Li、Xing Sun、Yulei Qin 等个人主页 | 只收录公开写明当前任职的人物样本 |
| 论文候选集 | 负责人论文索引 | 标记为“负责人公开论文索引” |
| 强归属论文 | Youtu 官方研究仓库 | 标记为“Youtu 官方研究仓库” |
| 项目生态 | 当前负责人公开项目列表 | 保留项目原始组织和链接 |
| 研究方向 | 论文标签、项目和 Abstract | 分别展示，不混为单一结论 |
| 关键词视图 | 31 篇可获取 Abstract 的论文 | 与 40 篇总工作集分母分开 |

Youtu 案例最值得复用的不是视觉样式，而是以下判断顺序：

1. 先承认旧官网不再完整；
2. 再寻找维护中的公开节点；
3. 用当前人物任职证明研究网络仍然存在；
4. 从负责人索引和官方仓库建立论文候选集；
5. 为每篇论文保留归属类型；
6. 用 Abstract 和项目活动总结研究重心；
7. 在页面中公开说明证据边界。

## 13. 为下一个团队创建页面时的最小交付物

建议至少创建：

```text
site/<team>.html
site/assets/<team>.css
site/assets/<team>.js
site/data/<team>-research.json
site/scripts/sync_<team>_research.py
```

如果有足够 Abstract，再创建：

```text
site/data/<team>-keywords.json
site/assets/<team>-keywords.png
site/scripts/build_<team>_keywords.py
```

同时更新：

- 站点构建入口和路由；
- 主目录中的团队深链接；
- 维护文档中的数据文件和命令；
- JSON 与 JavaScript 校验；
- 页面数据更新时间。

一个团队只有在身份、当前活跃、人物任职和论文归属都形成可解释证据链后，才适合做成与 Youtu 同等级的独立研究档案页。
